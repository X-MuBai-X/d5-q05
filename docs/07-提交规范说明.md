## 1. 格式

```
[类型] [版本号] [需求/Bug编号] 描述
```

- 方括号是**字面量的一部分**，提交消息里必须保留。
- 类型、版本号、编号之间用**一个空格**分隔；编号与描述之间也用一个空格。

## 2. 类型与必填规则

| 类型 | 用途 | 版本号 | 编号 |
|---|---|---|---|
| `feat` | 新增功能需求 | 必填 | 必填 |
| `fix` | 修复 Bug | 必填 | 必填 |
| `hotfix` | 线上紧急修复（事后补编号） | 必填 | 可选 |
| `opt` | 项目优化（性能、代码质量、重构） | 必填 | 可选 |
| `docs` | 文档变更 | 可选 | 可选 |
| `test` | 测试相关 | 可选 | 可选 |

## 3. 其它规则

1. **描述使用中文，简洁明了**，一句话说明这次改了什么。
2. **版本号格式**：`v{主版本}.{次版本}.{修订号}`，如 `v2.1.0`。
3. **编号**是飞书（Meegle）项目的工作项 ID，格式 `#数字`。
4. **一次 commit 只包含一个类型**；混合变更必须拆成多次提交。
5. **不使用** `<type>(scope)` 这类个人风格格式。

## 5. 本项目的提交分组

按「一次提交只含一种类型」的要求，提交按阶段拆分：

| 阶段 | 类型 | 说明 |
|---|---|---|
| 需求分析与项目约定 | `docs` | 需求分析、原型、任务规划、假设清单、AGENTS 约定 |
| 业务实现 | `feat` | domain / store / service / upstream / httpapi / cmd |
| 缺陷修复 | `fix` | 单元测试暴露的真实缺陷（模板、外键、表单编码、错误泄漏、并发幂等） |
| 测试 | `test` | 单元测试与覆盖率 |
| 工具与流程 | `opt` | 自编 Skill、脚本、CI 流水线 |
| 证据与说明 | `docs` | 部署说明、Skill 使用记录、AI 使用说明、会话导出 |

实际提交历史见 `git log --oneline`。
