## 1. 需求分析阶段假设 A1–A13

### A1 两个企业管理员分属两个不同租户

| 项 | 内容 |
|---|---|
| **假设内容** | 预置的两个客户管理员分别属于两个不同租户（`tenant-a` / `tenant-b`），而非同一租户下的两名管理员 |
| **为什么需要这个假设** | 题面只写「预置两个企业管理员和一个运营账号」「一家客户…另一家客户…」，以及「日终核查要求两个租户的数据隔离」，**未直接说明**两个管理员是否分属两租户 |
| **本项目如何实现** | 种子数据建立两个租户（初始日额度各 10）与两名管理员各挂一个租户；两名管理员口令不同，`admin-a` 属 `tenant-a`，`admin-b` 属 `tenant-b` |
| **若假设不成立的影响** | 若两管理员同租户，则无法验证「管理员查他租户 → 拒绝」（R7）、「两个租户的数据隔离」（题面第五组场景）与跨租户越权拒绝，日终核查的隔离验证需重新设计 |
| **证据路径** | `cmd/server/main.go:151-156`（两个租户与管理员定义）、`cmd/server/main.go:191-199`（写管理员并绑定租户）、`cmd/server/main.go:203-215`（运营账号无租户）、`internal/store/schema.sql:14-21`（`admins.tenant_id`）、`docs/01-需求分析.md` §2 |

### A2 「参数」= 模型名 + 提示词 + 业务参数的规范化摘要

| 项 | 内容 |
|---|---|
| **假设内容** | R3 中「相同编号与参数」「改参数复用编号」的「参数」，指参与上游调用的业务参数，即模型名 + 提示词 + 其他参数，规范化后取 SHA-256 摘要记为 `params_hash` |
| **为什么需要这个假设** | 题面 R3 只说「参数」，**未列举**参数集合，也未说明比较方式（整体比较、逐字段比较还是摘要比较） |
| **本项目如何实现** | `ParamsFingerprint` 将 `{model, prompt, params}` 组装为规范结构，剔除 `nil` 参数并按键排序后 JSON 序列化取 SHA-256；同编号同摘要视为幂等，同编号异摘要视为冲突 |
| **若假设不成立的影响** | 若「参数」应包含请求体中不影响上游结果的字段（如客户端备注），则幂等判定会误判为「同编号异参数」而拒绝本应幂等的重复请求；若应排除部分字段，则同编号会被误判为幂等而放过真实的新调用 |
| **证据路径** | `internal/domain/domain.go:294-321`（`ParamsFingerprint`）、`internal/domain/domain.go:303-313`（归一化）、`internal/service/service.go:378-390`（摘要比对与冲突拒绝）、`internal/store/schema.sql:44`（`params_hash` 列） |

### A3 2 秒超时从「发起上游调用」起算

| 项 | 内容 |
|---|---|
| **假设内容** | R4 的 2 秒时限从平台**发起上游调用**的时刻起算，而不是从首次受理或从排队开始计时 |
| **为什么需要这个假设** | 题面只写「超过 2 秒按本题规则判超时」，**未说明**计时起点 |
| **本项目如何实现** | 超时阈值常量 `UpstreamTimeout = 2 * time.Second`；受理并占用额度后立即调用上游，把该阈值作为调用时限传入 |
| **若假设不成立的影响** | 若应从受理时刻起算，则受理与写入的耗时会被计入 2 秒，导致实际留给上游的时间不足，超时率偏高、可用额度被提前释放 |
| **证据路径** | `internal/domain/domain.go:81`（阈值常量）、`internal/service/service.go:494-496`（以该阈值发起调用）、`internal/upstream/upstream.go:38-42`（`Complete` 契约）、`cmd/mockupstream/main.go:113-119`（超时场景挂起 30 秒） |

### A5 失败与超时是两个可区分终态，但计量口径相同

| 项 | 内容 |
|---|---|
| **假设内容** | 上游明确失败（`failed`）与超过 2 秒（`timeout`）是**两个独立终态**，分列统计；但两者**计量口径完全相同**：都释放额度占用、都不计入成功量 |
| **为什么需要这个假设** | R4 把「上游明确失败或超过 2 秒」并列书写，看起来像合并为一个终态；但 R8 要求日终「列出成功、失败、超时、处理中和被拒绝请求」，失败与超时在 R8 中是分列的两类 |
| **本项目如何实现** | 终态枚举分列；结算函数 `settle` 分三条分支：成功（处理中 −1、成功 +1，总占用不变），失败（处理中 −1），超时（处理中 −1）；日终报表按终态分列计数 |
| **若假设不成立的影响** | 若必须合并为单一「失败」终态，则 R8 的五类分列退化为四类，`timeout` 的独立计数与页面列需要调整；当前状态机与报表结构都要改 |
| **证据路径** | `internal/domain/domain.go:48-55`（终态枚举）、`internal/service/service.go:526-551`（`settle` 三分支）、`internal/domain/domain.go:378-385`（`StatusOrder`）、`internal/httpapi/web/templates/ops.html:51-53`（页面五列）、`docs/01-需求分析.md` §9 的 Q1 |

### A6 日额度为租户级单一数值，非「每凭证一份」

| 项 | 内容 |
|---|---|
| **假设内容** | 配额是**租户级**的一个数值，租户下所有凭证共享；运营为该租户设置**一个**日额度 |
| **为什么需要这个假设** | R2 说「同一租户的所有凭证共享日额度」，但**未说明**配置粒度是租户还是凭证，也未说明是否允许「基础额度 + 每凭证附加额度」这类组合 |
| **本项目如何实现** | `tenants.daily_quota` 为租户唯一额度字段；`tenant_day_usage` 按 `(tenant_id, day)` 计数，不含凭证维度；额度占用与降额下限均按租户聚合 |
| **若假设不成立的影响** | 若允许每凭证独立额度，则「不能通过换凭证绕过租户总额度」这条底线需要额外加租户级总闸；数据模型需增加凭证级额度字段，占用判定与降额下限口径都要重写 |
| **证据路径** | `internal/store/schema.sql:10`（`daily_quota` 在 `tenants` 表）、`internal/store/schema.sql:81-87`（用量表主键为租户+日）、`internal/store/store.go:545-561`（按租户原子占额度）、`internal/domain/domain.go:268-278`（占用与剩余口径） |

### A7 幂等命中返回首次受理记录的当前状态

| 项 | 内容 |
|---|---|
| **假设内容** | 同编号同参数的重复请求返回**首次受理那条记录的当前状态**；不新增记录、不占用额度、不调用上游 |
| **为什么需要这个假设** | R3 说「重复请求不能再次调用上游或重复计量」，**未说明**响应体返回什么——是返回首次受理时的状态快照，还是返回该记录的最新状态 |
| **本项目如何实现** | 命中时读取既有 `model_requests` 记录并原样返回（若该记录此后已完成，返回的是它的完成态），同时把 `replay_count` 加一作为幂等命中痕迹 |
| **若假设不成立的影响** | 若应返回首次受理瞬间的快照，则需额外持久化受理时状态字段；当前「返回记录当前状态」的行为会让重放方看到比首次调用更晚的终态 |
| **证据路径** | `internal/service/service.go:385-405`（幂等分支）、`internal/store/schema.sql:53`（`replay_count`）、`internal/httpapi/web/templates/admin.html:71`（页面展示「幂等命中」列） |

### A8 停用后旧编号请求走幂等路径，不计入拒绝类

| 项 | 内容 |
|---|---|
| **假设内容** | 凭证或租户停用后，用**旧编号**再次请求走幂等路径（返回原记录、不触发新的上游调用），**不**计入日终的「被拒绝」类 |
| **为什么需要这个假设** | R6 说「停用凭证不能通过再次请求旧编号触发新的上游调用」，但**未说明**该请求在日终报表中算「幂等命中」还是「被拒绝」 |
| **本项目如何实现** | 受理顺序中**幂等判定先于**租户/凭证状态校验；因此旧编号命中幂等分支直接返回，不进入状态校验，也不会写 `rejected_attempts` |
| **若假设不成立的影响** | 若应计入「被拒绝」，则需在幂等命中时额外写一条 `rejected_attempts`，日终「被拒绝」计数会包含幂等重放，「拒绝」的口径就不再等于「受理前被拒」 |
| **证据路径** | `internal/service/service.go:383-410`（幂等分支）位于 `:412-437`（状态校验）之前、`internal/service/service.go:583-596`（`recordRejected` 仅在拒绝分支调用）、`internal/httpapi/web/templates/admin.html:76-89`（被拒绝尝试表） |

### A9 应用角色不能查询租户级用量汇总

| 项 | 内容 |
|---|---|
| **假设内容** | 「普通应用仅可查询由其凭证创建的请求」意味着应用**无权**访问租户级用量汇总接口 |
| **为什么需要这个假设** | R7 列出管理员可看「本租户全部调用、成功量、处理中量和剩余额度」，应用的范围是「由其凭证创建的请求」，**未直接点名**用量汇总接口的归属 |

| 项 | 内容 |
|---|---|
| **假设内容** | 受理前被拒绝的调用尝试**落一条记录**用于日终「被拒绝」计数；该记录不占用额度、不计入成功量 |

### A11 租户停用后其凭证状态不变；凭证停用独立于租户停用

| 项 | 内容 |
|---|---|
| **假设内容** | 停用租户**不联动**停用其下凭证（凭证状态保持 `active`）；反过来，停用凭证**不**停用租户。两个状态各自独立 |

### A12 日终一致性核查口径：成功记录数 == 计入用量次数

| 项 | 内容 |
|---|---|
| **假设内容** | R8「核查成功记录与用量是否一致」的「用量」特指**计入用量次数**，即成功计数；一致性判定为 `成功记录数 == 计入用量次数` |
| **为什么需要这个假设** | R8 的「用量」**未定义**：可以指当日全部请求数、占用额度（成功+处理中），或计入用量的成功数 |
| **本项目如何实现** | `BuildDailyReport` 比较终态计数中的 `success` 与用量口径中的 `usage.Success`，不一致时生成差异说明文案 |
| **若假设不成立的影响** | 若「用量」指占用额度（成功+处理中），则存在在途请求时必然「不一致」，核查结论会持续为异常，运营将无法据此判断统计错误 |
| **证据路径** | `internal/domain/domain.go:349-368`（`BuildDailyReport` 与 `MismatchNote`）、`internal/httpapi/web/templates/ops.html:65`（页面「一致性」列）、`internal/domain/domain.go:278`（`Occupied`） |

### A13 教学时钟偏移仅影响「当前时间」，不改变配额与归属规则

| 项 | 内容 |
|---|---|
| **假设内容** | 教学时钟偏移只改变系统看到的「当前时间」，因而改变 UTC 自然日边界；配额上限、降额下限、归属规则、2 秒超时等业务规则**本身不变** |
| **为什么需要这个假设** | 共同要求第 1 节第 9 条允许「可配置教学时钟或缩短时长演示」，但**未说明**时钟是否可能影响超时阈值等判定基准 |
| **本项目如何实现** | 偏移通过 `OffsetClock` 叠加在系统时间上；`OffsetClock.Now()` 只影响 `Now()`；超时判定用的是 `domain.UpstreamTimeout` 常量而非时钟差；`day` 仍按偏移后的 UTC 日期计算 |
| **若假设不成立的影响** | 若时钟偏移同时要影响 2 秒超时阈值，则跨日演示时可能出现「按偏移后时钟判超时」的口径混乱，R4 的 2 秒规则将不再是固定值 |
| **证据路径** | `internal/service/service.go:36-50`（`OffsetClock`）、`internal/service/service.go:98-102`（`SetClockOffset`）、`internal/service/service.go:494-496`（超时用常量而非时钟差）、`internal/httpapi/server.go:464-485`（调整接口，注释「教学时钟只偏移『当前时间』，配额与归属规则不变」）、`internal/store/schema.sql:139-143`（偏移持久化） |

## 2. 交付后新发现的假设与澄清

以下事项在需求分析阶段**未被识别**，是在实现过程中暴露出来、必须做出选择的地方。每条给出「选择 / 理由 / 影响 / 证据」。

### N-01 运营账号没有租户归属，因此不能代客户创建凭证

| 项 | 内容 |
|---|---|
| **选择** | 创建凭证与停用凭证两个接口**只允许客户管理员**（`tenantAdminOnly`）；运营虽有 `adminOnly` 读权限，但**不可**写凭证 |

## 3. 假设的推翻流程

当题面信息补充、教师确认结论变化或演示环境限制变化时，按下列顺序处理，避免「口头改口径」：

1. **定位**：在本表找到受影响的编号（假设用 A 系列，交付后新增用 N 系列）。
2. **记录**：在 `docs/01-需求分析.md` §8 或 §9 写明新的结论与依据（`AGENTS.md` §1.3：不得在代码里私自改变业务口径）。
3. **对齐约定**：若涉及计量口径或身份权限，同步修改 `AGENTS.md` 的硬约束条款，并按 §10 的版本历史新增版本号。
4. **改实现**：只改 `internal/domain`、`internal/store`、`internal/service` 三层的对应逻辑。
5. **补测试**：按 `AGENTS.md` §4 注的要求，同步补充或修改三层的单元测试。
6. **跑守卫**：调用 `skills/quota-guard` 核验 R2/R4/R5 口径未被破坏，并把原始输出存入 `evidence/`。
7. **回写本文**：在对应条目上标注「已被推翻 / 已更新」，并指向新的结论位置。
8. **留痕**：按 `AGENTS.md` §8 的提交格式提交，编号核验情况如实记录（当前编号核验状态见 N-06）。
