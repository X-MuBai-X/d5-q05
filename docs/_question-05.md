## 题目 05：企业模型服务的配额开通、调用、停用与用量核查

**岗位来源**：[北京荆华密算科技｜Golang](https://www.zhipin.com/job_detail/b08ae08dd19d29200nN72Ny5GVFY.html)。CSV 职责摘录：“扩展模型接入、渠道管理、配额、限流、智能路由与计费结算能力”“用量对账脚本”。

### 业务背景与现场情境

模型 API 平台面向企业客户提供统一调用入口。运营为客户开通租户、配置日请求额度，客户管理员创建给应用使用的访问凭证，应用通过凭证发起调用。运营需要在客户咨询额度或故障时，说明请求是否实际执行、是否计入用量，以及停用后哪些请求仍可能完成。

一家客户在演示活动前临时增加额度，两个内部应用同时调用，接近上限时不断重试。另一家客户发现凭证可能泄露，要求立即停用。与此同时，上游模型有请求失败和超时，晚到的结果与重复请求容易把统计弄乱。客户不能因为平台统计错误被提前拦截，也不能通过换凭证绕过租户总额度。

你需要实现两家企业从开通到日常使用、额度调整、凭证停用和日终核查的小型运营场景。

### 参与角色与业务起点

- 平台运营：开通、停用租户，设置和调整配额，查看异常及用量。
- 客户管理员：管理本租户应用凭证，查看本租户调用情况。
- 客户应用：使用凭证调用模型、查询自己请求的结果。
- 模拟模型供应商：返回成功、明确失败或超过时限的响应。

预置两个企业管理员和一个运营账号；每个企业初始日额度 10 次，最多创建 2 个凭证。仅支持一个非流式文本模型，不进行货币或 Token 结算。

### 需要完成的业务范围与规则

1. 运营为租户开通服务并设置额度，管理员创建凭证；凭证所属租户由系统确认，不允许通过请求参数改成其他租户。
2. 同一租户的所有凭证共享日额度，按 UTC 自然日、首次受理时间归属。成功请求消耗一次，处理中请求计入额度占用，防止并发超过上限。
3. 请求必须携带本租户全局唯一编号；相同编号与参数重复请求不能再次调用上游或重复计量，改参数复用编号须拒绝，不因跨日而允许复用。
4. 上游明确失败或超过 2 秒按本题规则判超时，释放额度占用，不计成功量；迟到结果只保留为诊断记录，不改变已经返回的超时结论或追加扣额。
5. 运营可以提高额度；降低额度时不得低于当日已成功数量加处理中数量。每次变更记录操作人、原因和生效时间，不改变既有请求编号和日期归属。
6. 管理员停用凭证或运营停用租户后，不再受理新调用；已受理请求正常结束并按原规则计量。停用凭证不能通过再次请求旧编号触发新的上游调用。
7. 管理员可查看本租户全部调用、成功量、处理中量和剩余额度；普通应用仅可查询由其凭证创建的请求。运营可跨租户核查，其他角色不可越权。
8. 日终能够按租户、日期列出成功、失败、超时、处理中和被拒绝请求，核查成功记录与用量是否一致，说明每次额度变化和停用影响。

### 必须演示的完整工作场景

- 开通使用：运营开通 → 管理员建两个凭证 → 两个应用调用 → 管理员查询共享额度。
- 活动增额：额度耗尽 → 运营增加额度 → 应用恢复调用；非法降额被拒绝并保留原因。
- 事故处置：存在在途请求时停用凭证或租户 → 新请求受限 → 原请求完成 → 运营查明最终用量。
- 上游异常：失败、超时、迟到成功、重复请求、最后一个额度的并发争抢，不得造成超额或重复计量。
- 日终核查：跨日请求及两个租户的数据隔离、普通应用与管理员权限差异均须可验证。

### 原型、Skill 与单日边界

原型须覆盖运营开通与额度、客户凭证及用量、调用演示和异常查询。业务 Skill 用于检查配额、请求身份、停用时点、调用结果和用量口径。

不改造完整 New API、不做计费、多模型、多渠道或真实厂商接入。须执行第一部分全部要求，不能只交限流或计数接口。
