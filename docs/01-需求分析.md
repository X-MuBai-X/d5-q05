## 1. 业务背景与范围

### 1.1 场景还原

模型 API 平台面向企业客户提供统一调用入口。**平台运营**为客户开通租户、配置日请求额度；**客户管理员**创建给应用使用的访问凭证；**客户应用**通过凭证发起调用。

平台运营日常要回答客户三类问题，这三点构成本题真正的业务目标：

1. 这次请求**是否实际执行**了？（是否调用了上游、是否仍在处理中）
2. 这次请求**是否计入用量**？（占用/消耗了日额度多少）
3. 停用之后，**哪些请求仍可能完成**？（在途请求的归宿）

题面「现场情境」给出的四类现实干扰，全部要在系统里被正确处理：

| 干扰 | 业务风险 | 题面对应规则 |
| --- | --- | --- |
| 演示活动前临时增加额度 | 应用被误拦，或额度加不上去 | R5 |
| 两个内部应用同时调用、接近上限时不断重试 | 超发（超额受理）、重复计量 | R2、R3 |
| 凭证可能泄露，要求立即停用 | 停用后仍被调用、停用触发新上游调用 | R6 |
| 上游失败/超时、迟到结果、重复请求 | 统计错乱，客户被提前拦截 | R3、R4 |

题面最后一句是**验收的底线**：「客户不能因为平台统计错误被提前拦截，也不能通过换凭证绕过租户总额度」。这条同时约束 R2（额度按租户而非按凭证）、R4（失败/超时不计成功量，释放占用）。

### 1.2 交付边界

**做**：单一非流式文本模型的调用入口；租户开通/停用；日额度设置与调整；应用凭证的创建/停用；请求受理、计量、超时判定、幂等；用量与日终核查；可操作页面；数据库持久化；模拟上游模型服务。

**不做**（题面「原型、Skill 与单日边界」明确排除）：改造完整 New API、计费/货币或 Token 结算、多模型、多渠道、真实厂商接入。

题面要求「不能只交限流或计数接口」——必须交付完整业务闭环（开通→调用→调整→停用→日终核查）与五组可演示场景。

## 2. 角色、权限与账号模型

题面「参与角色与业务起点」定义四个角色：

| 角色 | 题面职责 | 可操作范围 | 不可做 |
| --- | --- | --- | --- |
| 平台运营 | 开通、停用租户，设置和调整配额，查看异常及用量 | 跨租户：租户生命周期、配额变更、全部用量核查 | —（题面未限制） |
| 客户管理员 | 管理本租户应用凭证，查看本租户调用情况 | 本租户内：凭证增删/停用、本租户用量与调用记录 | 不可操作其他租户；不可自行调额 |
| 客户应用 | 使用凭证调用模型、查询自己请求的结果 | 发起调用；查询**本凭证创建**的请求 | 不可查询其他凭证/其他租户任何数据 |
| 模拟模型供应商 | 返回成功、明确失败或超过时限的响应 | 被平台调用 | — |

题面 R7 的关键句：「管理员可查看本租户全部调用、成功量、处理中量和剩余额度；普通应用仅可查询由其凭证创建的请求。运营可跨租户核查，其他角色不可越权。」

预置账号（题面「参与角色与业务起点」）：**两个企业管理员 + 一个运营账号**。结合 R2「同一租户的所有凭证共享日额度」，这两个企业管理员分属**两个不同租户**（题面「一家客户…另一家客户…」，且日终核查要求「两个租户的数据隔离」）。每个企业初始日额度 10 次，最多创建 2 个凭证。

> **解读 R7-A**：管理员的查询范围是「本租户全部调用」——包含本租户**其他凭证**创建的请求；应用的范围是「由其凭证创建的请求」。二者的边界是**凭证**，不是租户。
>
> **解读 R7-B**：R1「凭证所属租户由系统确认，不允许通过请求参数改成其他租户」——凭证与租户的绑定关系由服务端从凭证记录推导，请求体中即使携带 tenant/tenant_id 字段也**不得**被采信。这是防越权的核心，也是题面「不能通过随意修改请求中的用户编号越权操作」（共同要求第 1 节第 8 条）的落点。

### 2.1 认证与身份可信度

共同要求第 1 节第 8 条允许「账号可预置」，但要求「角色身份必须可信，不能通过随意修改请求中的用户编号越权操作」。

本实现采用**预置账号 + 登录会话**：

- 运营账号、两个企业管理员账号预置（用户名/口令在种子数据中定义）。
- 登录后换取服务端签发的会话令牌，后续请求携带令牌；服务端从令牌解析出**角色与租户归属**，绝不从请求参数读取身份。
- 应用侧使用**凭证**（API Key）认证：令牌由管理员创建凭证时签发，绑定到该凭证所属租户。应用据此获得的租户身份同样由服务端推导。

> **解读 R1-A**：题面说「运营为租户开通服务并设置额度，管理员创建凭证」。凭证是管理员为本租户应用创建的，**不能指定租户**。因此创建凭证的接口不接受 tenant 参数。

## 3. 领域模型与状态机

### 3.1 实体

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| Tenant 租户 | id、name、status(active/disabled)、daily_quota | 配额是**租户级**属性，不是凭证级 |
| Admin 管理员 | id、tenant_id、username、password_hash | 与租户 1:1 或 1:N；本实现 1:1 |
| Credential 凭证 | id、tenant_id、name、key_hash、status(active/disabled) | 最多 2 个/租户；状态独立于租户 |
| ModelRequest 调用请求 | id、tenant_id、credential_id、request_no、params_hash、status、received_at、completed_at、upstream_result、error_reason、day(UTC) | 计量与核查的基本单元 |
| QuotaChange 配额变更 | id、tenant_id、old_quota、new_quota、operator、reason、effective_at | R5 要求「记录操作人、原因和生效时间」 |
| Diagnostic 迟到诊断 | id、request_id、late_result、recorded_at | R4「迟到结果只保留为诊断记录」 |

### 3.2 调用请求状态机（R2/R3/R4/R6）

```
                    ┌──────────────── 被拒绝 ────────────────┐
                    │ (不占用额度、不计入成功)                  │
                    ▼                                        │
  受理 ──> 处理中 ──┬──> 成功    (消耗额度 1 次, 计入成功量)   │
   │                ├──> 失败    (释放占用, 不计成功量)        │
   │                └──> 超时    (释放占用, 不计成功量)        │
   │                                                          │
   │  迟到结果 ──> 仅写入 Diagnostic, 不改变状态、不追加扣额 ──┘
   │
   └──> 幂等命中(同编号同参数) / 编号冲突(同编号异参数) / 凭证停用 / 租户停用
        → 均不调用上游、不占用额度
```

**状态语义逐条对齐**

| 状态 | 占用额度 | 计入成功量 | 是否调用上游 |
| --- | --- | --- | --- |
| 处理中 | 是（占位） | 否 | 是 |
| 成功 | 是（转为实扣） | 是 | 是 |
| 失败 | 否（R4「释放额度占用」） | 否 | 是 |
| 超时 | 否（R4 同上） | 否 | 是 |
| 迟到成功（诊断） | 否（不追加扣额） | 否 | — |
| 拒绝 / 幂等命中 / 编号冲突 | 否 | 否 | 否 |

> **解读 R2-A（额度占用模型）**：题面 R2 说「成功请求消耗一次，处理中请求计入额度占用，防止并发超过上限」。因此「已用量」= 成功数 + 处理中数；处理中是**预占**，成功是**预占转实扣**，失败/超时是**预占释放**。
>
> **解读 R5-A（降额下限）**：题面 R5 说「降低额度时不得低于当日已成功数量加处理中数量」。这与 R2 的口径完全一致——下限 = 当日成功数 + 当日处理中数。这条自洽性是本题配额口径正确性的关键交叉验证，说明我的解读方向正确。

### 3.3 日期归属（R2）

「按 UTC 自然日、首次受理时间归属」：

- 请求归属的 `day` = **首次受理时刻**所在 UTC 自然日（不是完成时刻）。
- 跨日的在途请求仍归属**受理日**；完成时更新其状态但不迁移 `day`。
- 「不因跨日而允许复用」（R3）：请求编号的全局唯一性**不按日重置**——编号唯一性在租户范围内跨日仍然成立。

> **解读 R2-B**：题面 R5「不改变既有请求编号和日期归属」反向确认：日期归属一旦在受理时确定，后续任何操作（含配额调整、跨日完成）都不得改写。

## 4. 规则逐条解读

### R1 运营开通与管理员建凭证，凭证租户由系统确认

> **原文**：运营为租户开通服务并设置额度，管理员创建凭证；凭证所属租户由系统确认，不允许通过请求参数改成其他租户。

**解读**

1. 租户的开通与配额设置是**运营**的独占动作；凭证创建是**管理员**的独占动作。角色不可互换。
2. 管理员创建凭证时，凭证的 `tenant_id` 来自**该管理员的会话身份**，不接受请求参数指定。请求体若携带 `tenant_id`，服务端忽略或直接拒绝（实现取「拒绝并返回明确原因」，更易暴露越权意图，且可被测试断言）。
3. 运营开通租户时设定初始日额度。

**可验证验收条件**

- 管理员 A（租户甲）创建凭证，凭证记录 `tenant_id` = 租户甲；管理员 B（租户乙）无法让该凭证归属租户乙。
- 管理员携带 `tenant_id=租户乙` 调用创建凭证接口 → 拒绝，且不产生任何凭证记录。
- 运营可跨租户为任一租户设置额度；管理员调用调额接口 → 拒绝（越权）。

### R2 共享日额度、UTC 自然日、首次受理归属、处理中占位

> **原文**：同一租户的所有凭证共享日额度，按 UTC 自然日、首次受理时间归属。成功请求消耗一次，处理中请求计入额度占用，防止并发超过上限。

**解读**

1. **配额是租户级**：租户甲的两个凭证共用同一份日额度，不能「换凭证绕过租户总额度」（题面现场情境原文）。
2. **日界为 UTC 00:00**。本地时区不参与计算。
3. **归属日 = 受理时刻的 UTC 日期**，受理后固定不变。
4. **并发上限**：受理时若 `当日成功数 + 当日处理中数 >= 当日额度`，则拒绝受理（不调用上游）。
   - 这要求受理路径具备**原子性**——同一租户的并发受理必须串行化判定。SQLite 下以事务 + 条件更新实现；或在服务层用租户级互斥 + 数据库唯一约束双保险。
   - 「最后一个额度的并发争抢」（必演场景）正是对这条的并发验证。

**可验证验收条件**

- 租户甲额度 1，两个凭证并发发起 10 个请求 → 恰好 1 个成功受理，其余 9 个被拒绝；库内成功+处理中不超过 1。
- 额度 2 的租户，1 个成功 + 1 个在途 → 剩余可用 0。
- 额度 10 的租户，两凭证各发起 5 次 → 管理员看到本租户成功量 10、剩余 0。

### R3 请求编号全局唯一、幂等、参数一致性、跨日不复用

> **原文**：请求必须携带本租户全局唯一编号；相同编号与参数重复请求不能再次调用上游或重复计量，改参数复用编号须拒绝，不因跨日而允许复用。

**解读**

这是本题最精细的一条，含四个子要求：

| 子要求 | 行为 | 依据 |
| --- | --- | --- |
| 必须携带编号 | 缺失/空 → 拒绝 | 「必须携带」 |
| 同编号 + 同参数 | **幂等**：返回首次结果，不再调用上游，不再计量 | 「不能再次调用上游或重复计量」 |
| 同编号 + 异参数 | **拒绝**：编号冲突 | 「改参数复用编号须拒绝」 |
| 跨日复用 | 仍然拒绝/仍然幂等，编号唯一性**不随日重置** | 「不因跨日而允许复用」 |

**「参数」如何定义**：题面未列举参数集合。本实现取**参与上游调用的业务参数的规范化摘要**（模型名 + 提示词 + 影响结果的参数），计算为 `params_hash`。同编号不同 `params_hash` → 冲突拒绝。

> **解读 R3-A（幂等的「不重复计量」语义）**：同编号同参数的重复请求返回首次受理的那条记录的状态；**不新增记录、不占用额度**。这与 R4「迟到结果不追加扣额」共同保证「一个编号最多贡献一次计量」。
>
> **解读 R3-B（幂等命中是否消耗调用次数）**：不消耗。幂等命中是「查已有结果」，不是新调用。

**可验证验收条件**

- 同编号同参数调用两次 → 上游调用计数为 1，库内该编号记录数 1，额度只被扣 1 次。
- 同编号改参数 → 拒绝，返回编号冲突原因。
- 同编号跨日（教学时钟推进到次日）再提交 → 仍为幂等命中/冲突，绝不成为新请求。

### R4 上游失败/超时、释放占用、迟到结果仅作诊断

> **原文**：上游明确失败或超过 2 秒按本题规则判超时，释放额度占用，不计成功量；迟到结果只保留为诊断记录，不改变已经返回的超时结论或追加扣额。

**解读**

1. **超时阈值 2 秒**，从「发起上游调用」起算（受理后立即发起）。
2. **两类失败等价**：上游返回明确失败 **或** 超过 2 秒 → 判为失败态，**释放额度占用，不计成功量**。题面在此把两者并列为同一处理分支（「按本题规则判超时」——指按本题规则归入失败/超时这一类不计量分支）。终态命名上，我区分 `failed`（上游明确失败）与 `timeout`（超 2 秒）两种原因，但**计量口径完全相同**（释放占用、不计成功），这样 R8 的日终核查才能分别列出「失败、超时」两类。
   > 依据 R8 原文「列出成功、失败、超时、处理中和被拒绝请求」——失败与超时在日终核查中确实是**分列的两个类别**，因此终态必须能区分二者；R4 的「按本题规则判超时」是在讲**计量规则**统一，不是在讲状态合并。
3. **释放占用**：失败/超时后，该请求占用的额度名额归还租户当日额度，租户可再次发起调用。
4. **迟到结果**：上游在 2 秒之后才返回（例如 2.5 秒才成功）。此时请求已按超时结案。迟到到达的结果**只写入 Diagnostic 表**：
   - 不修改该请求的终态（仍为超时）；
   - 不追加扣额；
   - 不计入成功量。
   > 迟到结果的捕获需要平台在 2 秒超时后**仍继续等待上游**并异步记录结果——这是本题技术实现上最容易被漏掉的一环：不能 `context` 取消后直接丢弃。
5. **重复通知/重复请求不弄乱统计**：R3 幂等 + R4 迟到诊断共同保证。

**可验证验收条件**

- 模拟上游返回 500 → 请求终态为失败，租户剩余额度 +1（占用被释放），成功量不增。
- 模拟上游挂起 >2 秒 → 2 秒后客户端收到超时结论；再过 0.5 秒上游返回成功 → 库内该请求仍为超时，Diagnostic 表有迟到成功记录，成功量未增加，额度未追加扣减。
- 额度 1 的租户：一次超时失败后，仍能再成功发起 1 次。

### R5 配额调整规则与审计

> **原文**：运营可以提高额度；降低额度时不得低于当日已成功数量加处理中数量。每次变更记录操作人、原因和生效时间，不改变既有请求编号和日期归属。

**解读**

1. **升额无限制**（受合理上界约束，见开放问题）。
2. **降额下限** = 该租户**当日**（UTC）成功数 + 处理中数。低于则**拒绝**并保留原因（必演场景明确要求「非法降额被拒绝并保留原因」）。
   - 注意下限用**当日**口径，不是历史累计。历史日的额度变更不影响。
3. **变更留痕**：`operator`（运营账号）、`reason`（原因，必填）、`effective_at`（生效时间）三者缺一不可。
   - 「原因必填」是我的解读：题面说「记录…原因」，若原因为空则审计无意义，故设为必填并在接口层校验。这是一个待确认点。
4. **不变更历史**：不改变既有请求编号与日期归属。

**可验证验收条件**

- 当日成功 3 + 处理中 2 = 5，降额到 4 → 拒绝，原因落库并可查。
- 降额到 5 → 成功，新额度生效。
- 任意变更后，既有请求的 `request_no` 与 `day` 不变。
- 变更记录含操作人、原因、生效时间。

### R6 停用时点与在途请求

> **原文**：管理员停用凭证或运营停用租户后，不再受理新调用；已受理请求正常结束并按原规则计量。停用凭证不能通过再次请求旧编号触发新的上游调用。

**解读**

1. **停用后拒绝新受理**：被停用凭证（或其所属租户被停用）的新调用立即被拒绝，不调用上游、不占额度。
2. **在途请求照常完成**：已受理（处理中）的请求在停用后**正常结束并按原规则计量**——成功则计入成功量并扣额度，失败/超时则释放占用。停用**不回滚**在途请求。
3. **停用后幂等仍成立**：用旧编号再次请求 → 返回已有记录，**绝不触发新的上游调用**（题面「停用凭证不能通过再次请求旧编号触发新的上游调用」）。
   > 这条把 R3 的幂等与停用串起来：停用不破坏幂等语义，旧编号请求返回历史结果而非新调用。

**可验证验收条件**

- 受理一个在途请求（模拟上游挂起）→ 停用凭证 → 该在途请求仍正常完成并按规则计量。
- 停用后用**新编号**调用 → 拒绝。
- 停用后用**旧编号**调用 → 返回原记录，上游调用计数不增加。
- 停用租户 → 该租户全部凭证的新调用均被拒绝；另一租户不受影响。

### R7 查询口径与越权边界

> **原文**：管理员可查看本租户全部调用、成功量、处理中量和剩余额度；普通应用仅可查询由其凭证创建的请求。运营可跨租户核查，其他角色不可越权。

**解读**

1. **管理员视图**：本租户全部调用记录 + 成功量 + 处理中量 + 剩余额度。
   - 剩余额度 = 当日额度 − (成功数 + 处理中数)。
2. **应用视图**：仅本凭证创建的请求。
3. **运营视图**：跨租户，可按租户/日期核查。
4. **越权一律拒绝**：管理员查他租户、应用查他凭证、运营以外角色跨租户 → 拒绝并返回明确原因。

**可验证验收条件**

- 管理员查本租户：可见另一凭证创建的请求。
- 管理员查他租户 → 拒绝。
- 应用查本凭证请求 → 成功；查他凭证请求 → 拒绝。
- 应用查「租户用量汇总」接口 → 拒绝（应用无该权限）。

### R8 日终核查

> **原文**：日终能够按租户、日期列出成功、失败、超时、处理中和被拒绝请求，核查成功记录与用量是否一致，说明每次额度变化和停用影响。

**解读**

1. **五类终态分列**：成功、失败、超时、处理中、被拒绝。
   - 「被拒绝」含：额度已满、凭证停用、租户停用、编号冲突、缺编号、参数不符等。
   > 「被拒绝」是独立于 R2 的**受理前**结论，故不占额度、不计成功量（见 3.2 表）。
2. **一致性核查**：成功记录数 == 该租户当日「计入用量」的次数。两者必须能对账，不一致要被报告出来。
3. **变更与停用影响说明**：日终报表需同时给出当日发生的配额变更（操作人/原因/前后值/生效时间）与停用事件（对象/操作人/时间/原因），使运营能解释「今天为什么这个租户用量长这样」。

**可验证验收条件**

- 按租户+日期查询，五类计数分别正确。
- 一致性核查返回「一致」，并给出对账明细（成功记录数 vs 计入用量数）。
- 报表含当日配额变更与停用记录。

## 9. 开放问题与确认结论

题面未明确且会改变实现结果的 12 项问题，已于 2026-11-11 与指导教师逐项确认。**以下为确认结论，实现必须严格遵循。**

| 编号 | 问题 | 确认结论 | 对实现的影响 |
| --- | --- | --- | --- |
| Q1 | 失败与超时是否为两个独立终态？ | **两个独立终态**，但计量口径完全相同（均释放额度占用、均不计成功量） | `failed` / `timeout` 分列存储与统计；R8 日终可分别计数 |
| Q2 | 降额下限用「当日」还是「历史累计」？ | **按 UTC 当日** | 下限 = 当日成功数 + 当日处理中数；历史日不参与判定 |
| Q3 | 应用能否查看租户级用量汇总？ | **不能** | 应用只能查询本凭证创建的请求；调用租户级汇总接口一律拒绝 |
| Q4 | 配额硬上界；工作项编号 | **① 设硬上界 100000；② 编号使用 `#6974499249`（按 commit-convention.md 示例）** | `domain.MaxQuota = 100000`；编号核验实况见 §11 |
| Q5 | 凭证数量上限「最多 2 个」 | **租户级硬上限，超出即拒绝** | 第 3 个凭证创建被拒绝并返回明确原因 |
| Q6 | 配额变更「原因」是否必填？ | **必填** | 为空则拒绝变更；变更记录必须含操作人、原因、生效时间 |
| Q7 | 被拒绝的请求是否落库？ | **落库到独立表，不占用 request_no 唯一性** | 新增 `rejected_attempts` 表；这样「额度耗尽→增额→应用用同一编号重试」仍然可用，不与 R3 幂等绑定冲突 |
| Q8 | 迟到结果保留形式 | **独立诊断表保留全部** | 运营可在日终报表与请求详情中看到迟到结果 |
| Q9 | 停用是否可逆？ | **不可逆**（安全侧倾向），接口保留 `status` 字段以便将来扩展 | 停用后只能新建凭证/重新开通租户 |
| Q10 | 日终核查默认「今日」 | **UTC 今日**，页面提供日期选择器可查任意历史日 | 日终报表支持任意日期入参 |
| Q11 | 迟到结果由谁产生 | **平台侧测试钩子模拟** | 平台提供受控的迟到注入钩子（仅测试环境可用），不依赖真实等待上游返回 |
| Q12 | 登录与身份可信度 | **预置账号 + 口令登录，服务端签发会话令牌** | 令牌承载角色与租户归属，身份完全由服务端推导，请求参数无法越权 |

### 9.1 关于 Q11 的实现说明（依确认结论）

迟到结果由**平台侧测试钩子**产生：受控钩子在请求已按 2 秒判超时并归还额度后，向 `diagnostics` 表写入一条 `late_result` 记录。该钩子**不修改**请求终态、**不追加扣额**、**不计入成功量**——这正是 R4 考察的口径。钩子仅在测试/演示环境启用，生产配置下不可用（见 `config.EnableTestHooks`）。

同时，模拟上游仍须能触发题面共同要求第 1 节第 5 条所列的「成功、失败、超时」场景（`cmd/mockupstream`），迟到诊断的**记录链路**与真实链路一致。

> **实现阶段的补充（不改变 Q11 的结论）**：五组完整场景逐条验证时发现，
> 「迟到结果」原先只能在进程内钩子里产生——平台在 2 秒判超时时会取消上游连接，
> 真实调用链路上**永远观测不到**上游迟到返回，题面「上游异常：迟到成功」这一场景
> 因此无法在可操作页面/接口上完整演示。
> 现已补充**真实迟到观测链路**：判超时后不取消上游调用，后台继续等待上游结果，
> 拿到后写同一条 `late_result` 诊断（口径与钩子完全一致：只写诊断、不改终态、不追加扣额）。
> 测试钩子作为确定性演示手段保留。详见 `docs/05-假设清单.md` N-02。

### 9.2 关于 R2 并发不变量的实现说明（独立验收 Agent 复核后补充）

题面 R2 要求「防止并发超过上限」。独立验收 Agent 在 2026-11-11 用
「1 次并发降额 + 5 次并发受理」的方式实测复现出：额度上限若以**参数**形式从业务层传入，
并发降额与并发受理交错时会出现 `占用数 > 日额度`（实测 `occupied=3, quota=0`，两次复现），
且此时日终报表仍返回 `consistent=true`，运营看不出超额。

据此把 R2 的实现口径收紧为两条硬性要求（已写入 `AGENTS.md` v1.4 §4 第 11/12 条）：

1. **额度上限的判定与计数必须在同一条语句内完成**，且额度上限由该语句**实时读取**
   `tenants.daily_quota`，不得使用业务层传入的快照值；
2. **降额下限的判定与写入同样必须在同一条语句内完成**，不得拆成「先读占用、再写额度」两步。

同时，日终报表除核对「成功记录数 == 计入用量次数」外，还必须核对「占用不超过额度」。
回归用例见 `internal/service/concurrency_test.go` 与 `internal/store/store_test.go`。
