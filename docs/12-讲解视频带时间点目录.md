## 1. 开场：这是什么题、解决什么问题（00:00 – 01:00）

| 画面 | 要讲 |
|---|---|
| 题面原文（R1–R8） | 模型 API 平台给企业客户开租户、配日额度、发凭证，调用要计量、失败和超时是两个终态，租户和凭证要能停用，运营要做日终用量核查 |
| `docs/01-需求分析.md` §9 | 题面没写死的 12 个口径（失败与超时是否同一终态、降额下限按哪天、被拒绝请求算不算占编号、停用能否恢复……）已逐项确认，实现按确认结论走 |
| `docs/02-原型设计.md` §2 | 三个角色的页面：运营 `/ops`、租户管理员 `/admin`、应用 `/app` |

**可核对点**：页面能打开、三个角色的菜单项与角色一致。

## 2. 场景一：开通使用（01:00 – 03:30）

| 时间 | 动作 | 预期现象（取自真实断言） |
|---|---|---|
| 01:00 | 运营登录 → 开通租户 tenant-a，设置日额度 10（**必须填原因**） | HTTP 200，额度=10 |
| 01:40 | 管理员登录 → 创建**第一个**凭证 | HTTP 200，密钥形如 `sk_…` |
| 02:00 | 创建**第二个**凭证 | HTTP 200 |
| 02:10 | 再创建**第三个**凭证 | **HTTP 400**，提示「凭证数量已达上限: 每个租户最多 2 个凭证」 |
| 02:30 | 应用一、应用二分别登录并各发起一次调用 | 均 HTTP 200，`status=success` |
| 03:00 | 管理员页看共享额度 | 成功=2，额度上限=10，**剩余=8**（两个凭证共享同一份额度） |
| 03:20 | 用应用身份访问管理员用量接口 | **HTTP 403**（越权被拒，不是 500） |

**要讲**：配额是**租户级单一数值**，多个凭证共享；权限边界是服务端强制的。

## 3. 场景二：活动增额（03:30 – 05:30）

| 时间 | 动作 | 预期现象 |
|---|---|---|
| 03:30 | 运营把额度压到当日已用量 | HTTP 200，额度=2（降到下限即被拒） |
| 04:00 | 应用再调用 | **HTTP 429**，提示「当日额度已用尽」 |
| 04:20 | 应用**用同一请求编号**再提交 | 仍是 **429「当日额度已用尽」**，**不是**编号冲突 —— 被拒绝的请求不占用编号 |
| 04:50 | 运营增额（填原因） | HTTP 200 |
| 05:10 | 应用用**同一编号**重试 | HTTP 200 `status=success`（编号未被占死） |
| 05:30 | 运营把额度降到低于当日已用量 | **HTTP 400**，提示「降低额度不得低于当日已成功数量加处理中数量: 当日已成功 3 + 处理中 0 = 3」 |
| 05:40 | 查看配额变更记录 | 记录了 operator、reason、effective_at |

**要讲**：降额下限是**当日成功数 + 处理中数**（按 UTC 当日）；被拒绝的请求进独立表，不占编号。

## 4. 场景三：事故处置（在途请求时停用）（05:30 – 08:00）

| 时间 | 动作 | 预期现象 |
|---|---|---|
| 05:30 | 企业乙管理员登录 → 建凭证 → 应用登录 | HTTP 200 |
| 06:00 | 发起一个会「处理中」的调用 | 在途请求已占额度，**处理中=1** |
| 06:20 | 管理员停用该凭证 | HTTP 200 |
| 06:30 | 应用再调用 | **HTTP 409**，提示「凭证已停用，不再受理新调用」 |
| 06:50 | 运营停用整个租户 | HTTP 200 |
| 07:00 | 应用再调用 | **HTTP 409**，提示「租户已停用，不再受理新调用」 |
| 07:20 | 等在途请求结束 | 终态 **timeout**，按原规则计量（释放占用、不计成功） |
| 07:40 | 运营查最终用量 | `counts={'failed':0,'processing':0,'rejected':3,'success':0,'timeout':1}` —— 超时与被拒绝**分列** |

**要讲**：停用**不可逆**；停用只影响**新受理**，在途请求照常按原规则收尾（这是最容易做错的一点）。

## 5. 场景四：上游异常与并发（08:00 – 11:00）

| 时间 | 动作 | 预期现象 |
|---|---|---|
| 08:00 | 调上游「失败」场景 | 终态 `failed`，**不**计入成功量，**释放**占用 |
| 08:40 | 调上游「超时」场景 | 终态 `timeout`，**耗时约 2.03 秒**（2 秒硬时限） |
| 09:10 | 调上游「迟到成功」场景 | 先按 `timeout` 结案；稍后运营页诊断区出现 **1 条 late_result**；**终态不变**、**不追加扣额** |
| 09:50 | 用**同一编号相同参数**再调 | `replayed=true` 幂等重放，**成功量只 +1** |
| 10:10 | 用**同一编号不同参数**再调 | **HTTP 409**，提示「请求编号已被占用且参数不一致」 |
| 10:30 | 把额度调成只剩 1 个名额，然后**8 个并发**争抢 | **成功 1，被拒 7**；并发未造成超额（成功量=5，额度上限=5） |
| 11:00 | 补充：额度上限与降额下限的判定与写入**在同一条语句**内完成，额度实时读取 | 展示 `skills/quota-guard` 的静态不变量输出（10 项全过） |

**要讲**：这是本项目最容易出错的地方——**失败/超时/迟到都不计成功量**，
**并发不能突破上限**（独立验收 Agent 曾实测复现过超发，已修复并有回归用例）。

## 6. 场景五：日终核查与权限（11:00 – 13:30）

| 时间 | 动作 | 预期现象 |
|---|---|---|
| 11:00 | 运营按租户与日期查五类计数 | `{'failed':1,'processing':0,'rejected':10,'success':5,'timeout':2}` |
| 11:20 | 看一致性核对 | `consistent=True`，用量=5 = 成功记录数=5 |
| 11:40 | 查另一个租户 | 两个租户数据**相互隔离**（tenant-b 的计数与 tenant-a 不同） |
| 12:00 | 已停用租户再查 | 成功量**不再增长** |
| 12:20 | 应用访问管理员用量/请求列表、查他人凭证的请求 | 均 **HTTP 403**；查**自身**凭证的请求 HTTP 200 |
| 12:40 | 运营**未指定租户**就查日终 | **HTTP 400**，提示「运营跨租户核查必须指定 tenant_id」 |
| 13:00 | 用教学时钟前移 48 小时 | 旧令牌全部失效（**401**），重新登录后可继续；跨日请求归属新的 UTC 自然日；次日只统计当日；原日统计不被污染 |

**要讲**：日终核查要能**发现不一致**（包括占用超过额度）；权限差异要在服务端强制；
跨日按 **UTC 自然日**归集。

## 8. 录制注意事项

1. **不要念完整口令**：页面与文档里都是掩码，完整值只保留在源码里，讲解时说「见部署说明」即可。
2. **每个异常分支都要展示状态码**（400/403/409/429）与提示文案，这是本题的核心考察点。
3. **不要展示任何令牌**：GitHub/Gitee 令牌只在环境变量里，不要出现在屏幕或口播中。
4. **视频时长不足时**，优先保证五组场景各一段 + 一个异常分支，其余可略过。
5. 录完把视频放到可访问位置（网盘/班级群均可），再把链接回填到
   `docs/11-班级群提交消息.md` §1 的「讲解与效果视频链接」处。
