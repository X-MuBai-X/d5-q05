# acceptance-audit — 验收逐条核查

## 1. 用途

题目 05 的验收看的是**逐条规则是否落地**，而不是"代码写得多不多"。本 Skill 把
`docs/_question-05.md`（题面快照）与 `docs/_common-requirements.md`（共同要求）
拆成可机器判定的检查项，对仓库逐一核对，输出：

- 每个检查项的结论：**pass**（有实现且有验证证据）/ **fail**（缺实现或证据不成立）/ **pending**（无法核验，如实标注）；
- 每项的**证据路径**（文件:行号 / 测试名 / 证据文件）；
- 一份可归档的 Markdown 报告 + 结构化 JSON。

**设计原则**：宁可标 `pending`，不可假装 `pass`。缺证据就是没通过。

## 2. 触发场景

| 触发场景 | 说明 |
|---|---|
| 交付前自查 | 提交最终交付物之前 |
| 按题目清单核对 | 评审者要求逐条说明"这条规则怎么实现的" |
| 整改后复验 | 修复缺陷后确认哪些检查项由 fail 转为 pass |
| 生成验收材料 | 需要一份可交给评审的逐条结论 |

## 3. 输入

| 参数 | 必填 | 默认值 | 说明 |
|---|---|---|---|
| `--repo` | 否 | 自动向上查找含 `go.mod`（module modelquota）的目录 | 仓库根路径 |
| `--out-dir` | 否 | `evidence/acceptance-audit` | 报告与 JSON 的输出目录 |
| `--skip-toolchain` | 否 | 否 | 跳过 gofmt / vet / test 等需要工具链的检查（结果记 pending） |

## 4. 执行步骤

1. **定位仓库**：向上查找 `go.mod` 中含 `module modelquota` 的目录。
2. **加载检查清单**：内置 R1–R8 与共同要求的检查项定义（见 §6），每项包含
   `id / 规则 / 判定方式 / 证据要求`。
3. **逐项判定**：
   - **实现类检查**用源码模式匹配（文件存在 + 关键实现片段出现）判定，
     命中即产出 `文件:行号` 作为证据；
   - **测试类检查**用测试函数名匹配判定；
   - **工具链类检查**实际执行命令，取退出码；
   - 任何一项找不到对应证据 → `fail`；因环境原因无法核验 → `pending`。
4. **执行工具链检查**（可跳过）：
   - `gofmt -l .` 输出为空；
   - `go vet ./...` 退出码 0；
   - `go test ./... -count=1` 退出码 0；
   - 覆盖率：解析覆盖率剖面，统计整体与核心包覆盖率，核心包下限 85%。
5. **产出**：`检查项明细.md`（Markdown 表格）+ `acceptance-audit.json`（结构化）+ 控制台摘要。

## 5. 输出格式

**Markdown（`检查项明细.md`）**

```markdown
# 验收逐条核查报告

- 仓库：<绝对路径>
- 结论：PASS / FAIL / PASS_WITH_PENDING
- 统计：pass 32 / fail 0 / pending 2

| # | 规则 | 检查项 | 结论 | 证据 |
|---|---|---|---|---|
| R1-1 | R1 | 凭证创建接口拒绝指定其他租户 | pass | internal/httpapi/handlers.go:45 |
| ... | | | | |

## 待补证

| # | 检查项 | 原因 |
|---|---|---|
| C-7 | GitHub PR / 分支保护记录 | 环境无 GitHub MCP 与 gh CLI，无法产生真实记录 |
```

**JSON（`acceptance-audit.json`）**

```json
{
  "repo": "...",
  "verdict": "PASS_WITH_PENDING",
  "stats": {"pass": 32, "fail": 0, "pending": 2},
  "items": [
    {"id": "R1-1", "rule": "R1", "name": "...", "status": "pass",
     "evidence": "internal/httpapi/handlers.go:45", "note": ""}
  ]
}
```

## 6. 检查项清单

### 业务规则 R1–R8

| # | 规则 | 检查项 |
|---|---|---|
| R1-1 | R1 | 存在按租户创建凭证的接口，且凭证所属租户由服务端从身份推导 |
| R1-2 | R1 | 创建凭证时指定其他租户被显式拒绝（越权不静默忽略） |
| R1-3 | R1 | 凭证数量有租户级上限（2 个） |
| R1-4 | R1 | 预置两个客户管理员与一个运营账号，初始日额度为 10 |
| R2-1 | R2 | 配额挂在租户上，租户下所有凭证共享同一份日额度 |
| R2-2 | R2 | 额度占用在数据库层以单条条件 UPDATE 原子完成（并发不超上限） |
| R2-3 | R2 | 存在并发争抢最后一个额度名额的测试，且只有一个请求成功 |
| R2-4 | R2 | 用量按 UTC 自然日归属，剩余额度 = 额度 − 成功数 − 处理中数 |
| R3-1 | R3 | 请求编号在租户内唯一，且有唯一索引保证 |
| R3-2 | R3 | 相同编号 + 相同参数 → 幂等命中，不重复调用上游、不重复计量 |
| R3-3 | R3 | 相同编号 + 不同参数 → 拒绝 |
| R4-1 | R4 | 成功 / 失败 / 超时是三个独立终态 |
| R4-2 | R4 | 失败与超时释放额度占用且不计成功量 |
| R4-3 | R4 | 超时阈值 2 秒 |
| R4-4 | R4 | 迟到结果只落诊断表，不改终态、不追加扣额 |
| R5-1 | R5 | 配额变更记录操作人、原因、生效时间 |
| R5-2 | R5 | 变更原因必填 |
| R5-3 | R5 | 降额不得低于当日成功数 + 处理中数 |
| R5-4 | R5 | 配额硬上界 100000 |
| R6-1 | R6 | 停用租户后不再受理新调用，已受理请求正常结束 |
| R6-2 | R6 | 停用凭证后该凭证不再受理调用 |
| R6-3 | R6 | 停用动作有事件留痕 |
| R7-1 | R7 | 存在运营 / 客户管理员 / 应用凭证三类身份与服务端签发的会话 |
| R7-2 | R7 | 身份与租户归属只来自服务端，请求参数中的租户编号不被采信 |
| R7-3 | R7 | 运营可跨租户核查，客户管理员与应用凭证仅限本租户 |
| R7-4 | R7 | 应用不能查看租户级用量汇总，仅限本凭证请求 |
| R8-1 | R8 | 提供日终核查报表，按成功 / 失败 / 超时 / 处理中 / 被拒绝分列 |
| R8-2 | R8 | 被拒绝请求单独计数（不占用请求编号） |
| R8-3 | R8 | 核对「成功记录数 == 计入用量次数」并给出一致性结论 |
| R8-4 | R8 | 报表含配额变更与停用影响 |
| R8-5 | R8 | 页面可指定日期查询（默认 UTC 今日） |

## 7. 失败处理

- **实现类检查失败** → 结论 `fail`，证据栏写明"未找到"，并在报告末尾给出修复方向。
- **工具链类检查失败** → 结论 `fail`，附命令原始输出（截断到 30 行）。
- **环境导致无法核验**（如无 GitHub MCP、目标空间不可见、无远程主机）→ 结论 `pending`，
  并在「待补证」中写明**具体原因**，不得写成 pass。
- **证据文件里出现明文口令 / 密钥** → C-14 直接判 `fail`，并指出文件路径与行号。
  C-14 的扫描**不含任何白名单或例外目录**：证据与文档里只要出现明文口令就判失败。
  预置演示账号的口令同样按明文处理，需要在文档中以掩码形式出现（如 `ops-****`），
  完整值只保留在源码这一唯一事实来源里。
- **禁止**为了让报告全绿而放宽判定标准、删除检查项或伪造证据。

## 8. 完成标准

1. 全部检查项都有明确结论（pass / fail / pending），无空缺；
2. 每个 pass 项都有可点击的证据路径；
3. 每个 fail 项都有失败原因；
4. 每个 pending 项都有具体的环境原因；
5. Markdown 与 JSON 两份产物都已落盘，控制台输出 ASCII 摘要；
6. 总体判定为 `PASS`（无 fail）或 `PASS_WITH_PENDING`（无 fail 但有 pending）；
   **存在 fail 时总判定为 `FAIL`**。

## 9. 快速使用

```powershell
python skills/acceptance-audit/scripts/acceptance_audit.py --out-dir evidence/acceptance-audit
```

退出码：`0` = 无 fail，`1` = 存在 fail，`2` = 执行错误。
